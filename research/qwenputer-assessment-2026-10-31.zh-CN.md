日期：2026-10-31

性质：技术审阅与研究提案；不是原作者论文，不是已经实现的新功能，也不是完整 GPU 复现实验报告。

## 核心判断

Qwenputer 的核心贡献不是第一次证明神经网络能够计算，也不是第一次把程序编译成 Transformer，而是把**可编程的确定性计算、可覆盖的精确状态、低精度数值实现和现成语言模型的接口**组合为一个可执行系统。值得重视的是这条工程链条，而不只是“LLM 内部跑 CPU”这个演示。

最有价值的思想是：可以把“必须保证的操作语义”与“需要从数据中学习的判断能力”分开。加法、地址更新、寄存器写入不必通过训练碰运气；决定算什么、何时读取什么，以及如何解释结果，仍然可以交给学习模块。

目前证据更支持“新的研究与构造方法”，而不是“比外部工具更快、更省内存或普遍更智能的产品”。真正值得推动的下一阶段，是让这种混合系统获得更明确的数值契约、更高效的执行后端，以及不依赖文本序列化的紧密接口，而不是继续增加套娃演示。

## 一、它究竟把什么编译进了模型？

需要区分四个对象：

| 对象 | 所在位置 | 是否通过这项工作训练得到 |
| --- | --- | --- |
| 语言理解与语言生成能力 | 预训练 Qwen 的原有参数子块 | 使用已有预训练结果 |
| CPU 的状态转移与控制规则 | 新增的编译层权重 | 否，编译器构造 |
| 程序、RAM、寄存器、PC | 编译层的 Gated DeltaNet 循环状态 | 运行时装载和改变，不是重新训练参数 |
| 解码调度、初始化、状态保存与恢复 | 宿主驱动及运行环境 | 普通软件职责 |

因此，“程序写进权重”需要精确理解：**CPU 的规则写进权重，CPU 执行的程序及数据主要装入状态。** 不是每换一个 C 程序就必须重新训练或重新生成全部 CPU 权重。[S1][S2]

当前 RISC-V 聊天路径大致是：

```text
Qwen 生成 calc 请求文本
        ↓
编译桥接电路捕获文本并启动固件
        ↓
编译 CPU 依据自身状态生成 trace token，并更新 DeltaNet 状态
        ↓
编译电路输出结果的普通文本 token
        ↓
Qwen 读到结果，继续组织答案
```

`RvChat` 在 chip token 阶段仅运行计算机层，避免把整个微执行轨迹送入原语言模型的层、缓存与 RoPE 位置；普通文本 token 才进入语言模型部分。这个隔离既是功能接口，也是减少无用计算、控制语言行为变化的重要措施。[S2][S3]

这不是“原来的 Qwen 突然理解了 RISC-V”，而是把能理解语言的模型和有确定执行语义的部件放进了兼容的计算体系中。

## 二、创新在哪里，又有哪些重要前人？

不能把全部相关思想都归为 Qwenputer 首创：

| 前人方向 | 已有内容 | Qwenputer 值得区分的部分 |
| --- | --- | --- |
| Neural Turing Machines，2014 | 可学习控制器与可读写记忆结合 | 核心 CPU 和读写语义不是从样本学出来，而是显式编译 |
| Fast Weight Programmers / Delta rule，2021 | 线性注意力与联想记忆、可纠正的 key-value 映射 | 将指定状态操作约束成可靠的精确可寻址存储，并承载完整机器 |
| Tracr，2023 | 将 RASP 程序编译成 Transformer 权重，提供解释性研究的真值 | 与预训练语言模型结合，使用有状态的实际指令执行系统 |
| Looped Transformers as Programmable Computers，2023 | 指定权重、循环执行、指令与程序计数器等计算机构造 | 具体落到 Qwen/GDN/SwiGLU、有限精度、软件工具链和长轨迹检查 |
| Gated Delta Networks，2025 | 门控、delta 更新及其高效循环结构 | 把现成结构用作可精确控制的计算底座 |

这些比较只是定位研究贡献，不构成穷尽所有同期工作的首创性证明。[P1–P5]

### 2.1 精确 RAM：把“混合过去的信息”变成“覆盖某个位置”

用行存储约定，令 `S` 为 `n × d` 状态矩阵；关闭遗忘、写入强度为 1，则简化 delta 更新可写为：

```text
S' = S + k (vᵀ − kᵀ S)
```

当 `k = e_i` 为第 i 个单位向量时：

```text
S'[i, :] = vᵀ
S'[j, :] = S[j, :]，j ≠ i
```

再以 `q = e_j` 查询，就得到第 j 行。这里重要的不是“相似的内容更容易被找回来”，而是“地址 i 的旧内容被新内容替换，其他地址保持不变”。这种可组合语义使寄存器、PC、栈、RAM 和文件目录成为可能。[S4][S5]

这一推导不代表任意 soft key 都能充当精确地址；soft key 通常会同时影响多个方向。它也不意味着固定大小状态可以容纳无限量信息。精确可寻址存储、语义联想和容量，是需要分别讨论的问题。

### 2.2 数值工程：在浮点网络中维持离散状态的不变量

公式正确并不足够。只要一次进位、一次分支判断或一次地址写入出错，后续轨迹就可能完全改变。工程难点是把所有可达中间值限制在适合目标精度的集合里，而不是把普通神经网络的近似输出当作数字电路。

源码中的关键处理包括：用 bit、nibble 和小整数分解宽整数；让激活落在 SiLU 与目标门函数按指定浮点行为一致的区间；为布尔门加入判定裕量；通过 ballast 使 RMSNorm 的缩放可预测并折叠进编译权重；在 IR evaluator 中检查中间值、门控以及 key/query 形状。[S4][S5][S6]

例如，32 位运算不是把任意 32 位整数原封不动塞进一个 BF16 标量，再期待乘加永远精确。它通过更小的离散表示及相应进位逻辑实现宽整数语义。

这里的“精确”必须附带运行条件：目标 dtype、允许的输入范围、数值内核、累加/舍入方式、归一化、状态初始化等。更换精度或随意量化，不能默认继承结论。BF16 与 FP16 的表示范围也不能混为一谈。作者的长轨迹测试是有价值的工程证据，但不是所有输入、所有后端上的形式化证明。

### 2.3 合成与学习共存，而不是重新学习一切

现有语言模型已经具备语言和工具调用习惯；编译层借用这种接口，而不要求从头训练语言能力。CPU 内部的确定性与语言模型选择操作的能力，可以分别维护、测试和升级。[S1][S2]

这种结构的潜在意义是“能力模块可以由程序构造后接入模型”，而不仅是增加训练数据。更新固件可以改变计算机能执行的程序；增加编译原语可以改变机器能力；适配器训练则可以改变模型如何使用它。三者不是同一类更新。

但必须强调，参数子块未重新训练，不等于增加层和改变执行图之后所有语言行为完全不变。上游报告的 KL 和有限提示词回归检查支持的是“所测试范围内变化较小”，不是全局无损定理。[S2]

## 三、实际优势：应当与哪个基线比较？

### 相比纯语言模型算术：优势直接且明确

把长整数乘除、地址更新或状态修改交给有明确语义的部件，就不再要求模型逐个猜数字。只要输入表达式正确、固件支持该表达式、执行条件满足，输出的运算结果由程序决定。主要收益是局部算法正确性和状态一致性，而不是语言推理本身突然提升。[S1][S2]

### 相比模型加外部工具：当前主要是架构与部署形式的区别

本地 Python 工具、传统 CPU、受控进程内解释器同样能提供精确运算。外部工具不一定意味着联网、RPC 或显著网络延迟，因此不能把那些开销自动算到外部方案上。

Qwenputer 展示的是：确定性计算可以用与模型兼容的结构表达、一起打包和检查，并在模型的内部执行路径中保留可操作状态。它为更紧密的表示交互留下了空间，但当前主要接口仍然是文本式工具协议。**同一操作放到模型内部，本身并不产生额外的智能或信息。** 若与一个语义相同、接口和预算相同的外部执行器比较，只改变物理位置，不应预设准确率必然提高。

### 相比仅用长上下文：改变了状态保存与更新的方式

精确存储可以覆盖旧值，而不必把“旧值、新值、解释更新原因的整段历史”都留给后续注意力重新处理。文件系统分支还可以把状态保存后在新会话恢复。[S7]

不过，这不是永久记忆自动出现。跨进程持续性依赖保存和恢复；文件系统容量有限；语言部分仍然可以有增长的 KV cache；文件名查找也不等于语义检索。对“如何组织经历、如何识别相关性、何时重新解释一段经历”，这个存储底座不提供完整答案。

### 相比重新训练专用模型：更容易定义局部契约

如果确定性模块的输入、输出、状态与数值前提都写清楚，就可以将“操作执行错了”和“模型选择错了操作”分开诊断。这个分解对长期维护、因果实验和验证很有价值，但同样需要系统性的契约设计，不能仅凭“没有训练”就声称实现没有 bug。

## 四、证据强度与版本边界

下表中的结果均为上游报告，非本次独立复现。

| 项目 | 已有证据 | 不应外推成什么 |
| --- | --- | --- |
| RISC-V 核心 | 指令测试、QEMU/参考机比较及大量 free-running 检查 | 完整特权架构、Linux 兼容或所有程序形式化正确 |
| P2 核心规模 | 11 层、1,040,595 个非零权重 | 完整模型只增加约 1M 的实际显存开销 |
| P3 合并模型 | 文档记录约 18.7 GB BF16 checkpoint；端到端 calc 可用 | 已经是高效的普通 CPU 替代品 |
| 算术评测 | 当前 README 每组 40 题；若干项目 39/40 或 40/40 | 显著优于语义匹配的外部工具 |
| 语言保持 | 16 个提示词的 KL 检查；10/16 greedy 文本相同 | 所有提示、所有 batch、所有后端 bit-identical |
| 文件系统 | 90 个跨会话问题、30 个更新事实问题，合成 LongMemEval-style 设置 | 正式完整 LongMemEval 或普遍长期记忆能力 |
| MicroPython | 审阅 P3 文档明确：独立核心和 executor 已跑通 | 当时合并聊天路径已支持 Qwen 随意生成并执行 Python |
| NPU / QwenPU | 作者已展示小模型作为 guest 程序执行 | 自我学习、自我改进或更经济的神经网络推理 |

### 4.1 分数应如何理解

40 题中相差一题就是 2.5 个百分点。README 中 97.5 与 100、95 与 97.5 的差距不足以单独证明内部工具优于外部工具；应当考虑配对题目、解码后端、相同操作语义、错误响应、预算和多次运行的不确定性。[S1][S2]

文件系统模型卡给出了更完整的基线：跨会话合成测试中，无历史的基础模型是 7.8%，将旧会话贴回上下文是 76.7%，内部文件系统是 83.3%，Python 文件工具是 78.9%。在发生更新的 30 个问题中，上下文回填为 30%，内部文件系统为 90%。这些结果提示显式状态更新有潜力，但不能把 7.8→83.3 全部归因为“存储在模型内部”的独有效果。[S7]

CHIP-8 旧版、RISC-V 当前版、文件系统分支、NPU 分支和独立 QwenPU 仓库不能混成同一个 checkpoint 的统一成绩。尤其不要把旧版 README 中不同开发 checkpoint 的最佳模式统计，视为一次固定配置的最终盲测。[S1]

### 4.2 “精确计算”不等于“正确回答”

P3 文档记录的失败包括：工具已经返回正确值，Qwen 又重算、丢失符号、给出另一个结果或反复调用直至预算耗尽。NPU 模型卡也记录了计算全部正确但重复调用导致端到端失败的情况。[S2][S8]

因此应分开报告：表达式选择正确率、执行成功率、执行值正确率、结果使用正确率、停止行为和最终答案正确率。把这些混成一个分数，会掩盖真实瓶颈。

## 五、源码审阅中值得单独记录的三个细节

### 5.1 默认 CLI 确实会执行参考模拟器，但用途是检查，不是替模型算答案

审阅基线的 `experimental/riscv/chipformer/rv/chat.py` 中，`main()` 会构建 `BR.Session`，并把它作为 `lock` 传入 `generate()`；生成循环中调用 `lock.qwen()` 得到预期 trace，发生不一致则停止。

但从该路径的数据流看，参考机的预期 token 没有被用于替换 `nxt`；下一 token 来自编译电路输出或 Qwen logits。`generate(..., lock=None)` 在接口上允许不做这个在线校验。[S3]

所以需要同时避免两种错误表述：“其实全是 Python 算的”与“宿主完全不执行任何相关计算”。更准确的表述是：**输出执行语义由编译电路承载；默认演示还伴随宿主初始化、调度及参考机检查。** 本次没有在 GPU 上独立复现关闭 lock 的运行。

### 5.2 stock 类可加载，不等于任意 stock generate 路径都等价

当前合并 RISC-V 的 `RvChat` 显式处理 trace token、状态注入以及计算机/语言模型的执行分离。博客也承认当前版本并非直接调用普通 `generate()` 就完成所有这些行为。CHIP-8 旧版及独立 `rv-tiny` 的 plain-generate 演示不能自动转移给 P3 合并聊天版本。[S2][S3][S9]

### 5.3 发布的 Triton 速度不一定是默认 CLI 采用的路径

`RvChat.__init__` 的 `executor` 默认是 `False`；审阅的 `main()` 只传入 `fast=not args.slow`，没有传入 `executor=True`。因此不能看到 README 的 Triton 数字，就默认 quickstart 命令必然按该模式运行。性能复现必须记录执行路径、设备、batch、是否在线校验，以及统计的是 trace tokens/s、instructions/s 还是完整问答耗时。[S3]

这些细节不会否定项目的核心构造，但会直接影响复现、性能比较以及宣传措辞。

## 六、以后可能真正突破的方向

以下为研究判断与提案，不是已经实现的能力，也不主张其全部属于无人研究的全新方向。

### A. 从精确 CPU 走向“带契约的可编译状态模块”

CPU 是很强的通用性演示，但不是所有任务的最优中间层。可以直接编译计数器、栈、结构化记录、有限状态解析器、事务更新、索引和检查器，而不必先转换成一长串通用指令。

建议为模块声明：输入值域、允许写入的状态区、输出类型、舍入和溢出行为、最大执行预算、可恢复错误、数值前提。学习模块只能经由受约束入口提出操作，不能直接任意扰动精确核心的中间表示。

长期目标是从“这组测试没有出错”推进到可组合证明，例如为逻辑状态与网络状态建立对应关系 R，并验证：

```text
R(s, h) 且输入 x 满足契约
    ⇒ R(F_spec(s, x), F_backend(h, encode(x)))
```

对小原语可做穷举及位向量验证，对长程序使用保持不变量的组合推理。数值内核、状态装载、桥接和采样也必须进入可信边界；不只证明理想实数公式。

潜在突破：模型可由“学习得到的能力”与“可验证的执行部件”组成，而不是只有一个无法区分责任的整体。但被验证的是契约内的操作，不是自然语言的真实性或价值判断。

### B. 从文本式工具协议走向受约束的 latent/tensor 接口

当前大部分内部交互仍是“生成工具调用文本→执行→读回文本”。下一步可以研究让模型的隐状态产生有类型的操作候选，把精确读出的值通过适配器返回表示空间，不必对每个中间操作都进行字符串序列化。

这可能减少调用格式错误、token 开销和反复解析，但不会自动减少所有推理错误，也不意味着 CPU 指令能够直接通过普通梯度无障碍训练。硬地址选择、离散分支和阈值门有真实的优化困难。可先冻结确定性核心，以监督操作轨迹训练接口，再谨慎比较离散训练方法；若采用软松弛，必须单独检查训练/推理差异。

关键对照不只是传统文本 Python 工具，还应包括**拥有相同 tensor 接口的外部/进程内确定性模块**。否则任何提升都可能只是来自更好的接口，而非“计算位于权重里”。

潜在突破：从“模型持有一个计算器”变为“精确状态操作参与表示更新”；是否产生新的能力，必须用因果干预和严格对照回答。

### C. 持续状态与语义演化：把存储正确性和理解能力解耦

值得研究的并非仅仅“文件没有丢失”，而是：同一条历史记录，在不同当前理解下具有不同意义；这种意义变化再影响下一步关注、推理和停止。

可以保留不可歧义的经历记录和状态版本，同时让预训练模型的表示形成可持续更新的理解状态。精确存储负责记录、覆盖、版本与引用一致性；学习模块负责语义重解释和当前相关性。两者不必使用同一种地址机制：语义选择可以是学习得到的，而最终提交可以有硬边界。

不能因为程序自己走了 100 步、RAM 不断变化、没有输出文本，就声称出现自主认知。普通 CPU 本来就会这样。更强的证据是：新的相关信息改变内部未解决问题，改变后续解释与访问，而不是仅仅改变一次固定检索的地址；回答已可读出与内部计算是否结束也应分别测量。

外部时钟和计算预算可以存在；外部调度器不应替模型规定每一步的语义内容。如果状态没有变，重复算子只是在空转，不能当作成功。

### D. FPGA 与多后端：同一份语义，不同的物理实现

把整个宽化 Qwen checkpoint 原样搬到 FPGA，并不是这里最自然的第一步。更加直接的路线是保留高层计算语义，并从同一 IR 产生多种实现：

```text
带类型、值域与状态读写语义的 IR
    ├─ GDN / SwiGLU 权重后端
    ├─ 稀疏或位打包的软件执行后端
    └─ RTL / FPGA 后端
```

重要的是从已知语义降低，而不是指望任意密集训练权重都能被反编译成精确电路。当前已有针对 IR 的 Triton executor，因此“利用稀疏性加速”本身已属于上游工作；新贡献应进一步涉及契约保持、位级化、自动调度和跨后端状态等价。[S2][S3]

在满足前提的子图中，one-hot delta 覆盖可以降低为存储器写入，离散阈值可以降低为比较器，常量乘法可以考虑移位与加法。可是多读端口、读写同址时序、全头清零、衰减和流水线停顿都不能凭空消失。尤其“数学上一个 gate 清零整个矩阵”并不自动等于 FPGA BRAM 能一拍清零所有地址；可能需要有效位/epoch 机制或多周期调度。

等价比较通常应当是**逻辑步骤或事务边界上的状态等价**，而不是神经 trace token 与 FPGA 时钟周期一一对应。目标硬件、资源利用率、外存带宽、跨设备通信、时延与能耗均需实测，不能由稀疏权重数推算。

神经网络到 FPGA 已有 FINN 等路线，不能把部署本身当成新发明。[P6] 这里更有针对性的研究问题是：能否让相同的确定性状态模块在模型内部与硬件中共享可验证的语义，并与学习模块有效协作？如果最后只是重新实现了一颗普通 RISC-V 软核，就应诚实地把结果归为编译/硬件工程，而不是新的智能机制。

### E. 已知真值的解释性与监测实验

编译构造的好处是知道一个机制在哪里、怎样工作，可以用来评估解释方法究竟找到了因果机制，还是仅拟合了相关性。但作者已经做了植入 tracker、检测器与状态日志等后续工作，Tracr 也早已提出相关真值测试思路，不能把这些整体作为新的原创提案。[S10][S11][P3]

更有价值的扩展，是让测试机制更接近训练得到的分布式表示，并检验跨任务、干扰、复制信息和状态迁移。任何重参数化都必须尊重激活和归一化语义，不能随意旋转整个网络再假定函数不变。

“模型不能通过普通提示词关掉固定门”不等于“监测器不可绕过”，更不等于“不会撒谎”。监测探针可能误判，模型可能不进入被监测状态，输出协议可能存在伪造写入途径，持有权重或执行环境的人还可以修改机制。应把威胁模型、观察范围和假设写清楚。

## 七、建议的实验顺序与否证条件

### 实验 0：建立分层复现边界

先分别记录：参考机、IR evaluator、真实 HF 编译层、Triton executor、完整 Qwen 聊天路径。固定代码 commit、固件、tokenizer、模型权重、dtype、kernel、batch、seed、预算和 lock 设置。

从少量已知程序开始，检查无参考纠正的 free-running 轨迹，并在事后比较；再扩展随机程序、算术边界、快照恢复和错误路径。teacher forcing、在线检查和 free-running 必须分开标注。在线校验允许报错，不允许修正输出后再统计成功。

最低产物应是能够明确指出“哪个层面错了”的报告，而不是只打印答案匹配率。

### 实验 1：语义保持的软件后端，先于 FPGA

选择小型 RAM、计数器/栈和一个算术模块，保留原状态语义，建立稠密数学表达、现有网络/IR 路径与位打包实现之间的差分检查。

测试同址覆盖、未写地址、边界地址、无效输入、溢出、清零、保存恢复和长序列；同时记录逻辑状态与输出，不只比较最终答案。小位宽可以穷举，较大范围使用随机与边界测试，并记录其不能替代证明。

如果不能保持状态对应关系，就停止硬件化扩展。若只获得普通程序执行优势，成果应定位为后端优化，而不是智能提升。FPGA 阶段再加入时序、读写冲突、端口资源、时钟与功耗测量，并与成熟软核或直接专用电路比较。

### 实验 2：内部文本、外部文本与 tensor 接口的公平对照

至少区分五种设置：基础模型；外部文本工具；当前内部文本工具；外部/进程内 tensor 接口模块；内部 tensor 接口模块。使用同样的操作语义、数据、容量、训练预算和计算预算。

分别统计请求是否正确、执行是否正确、结果是否使用正确、最终任务成功率、调用次数、文本 token 数、内部逻辑步骤、端到端时延和峰值内存。将语言文本预算与内部 trace 预算同时公开，不能把 trace token 当成免费计算。

冻结确定性核心，对接口训练进行版本化；训练后重新执行核心契约测试。如果内部接口的收益可以被外部 tensor 接口完全解释，则结论应是接口优化，而非内部执行具有独有智能优势。

### 实验 3：语义重解释与状态因果作用

设计同一经历在两种背景理解下意义不同的任务，避免只靠关键词匹配或一个隐藏离散标签就能得分。使用预训练模型已有表示，而不是要求一个从零训练的小控制器承担全部语义理解。

复制同一中间状态，分别注入解决当前疑问、引入相关矛盾、无关的信息；检查后续意义解释、信息访问、答案与停止行为是否按因果关系改变。额外交换或清除状态，阻断相关信息路径，并设置相同计算量但不保留历史的对照。

应分别读出“现在是否能回答”和“内部是否继续”。继续计算只有在改变相关理解或有效处理矛盾时才有意义；仅多走几步或提高固定任务分数，不足以证明自主认知。

若所有收益都能由更多上下文、更多计算、显式外部策略或隐藏答案提示解释，则保留机制层面的有限结论，不拔高为持续认知系统。

## 八、推荐的优先级

近期最可控的是**分层复现 + 状态/数值契约 + 语义保持的软件后端**，因为这些直接建立在现有代码上，失败原因也比较可定位。

中期最值得做严格比较的是**受约束的 latent/tensor 接口**，关键问题不是能否把值接进 hidden state，而是这是否真正减少序列化开销、提升状态使用质量，并且超越接口相同的外部对照。

更长线的是**持续状态与语义共同演化**。这可能具有更大的认知架构意义，但不能用 CPU 正确执行、文件系统召回或脚本自主循环替代证据。

FPGA 可以作为契约明确之后的第二后端，而不必成为第一道工程门槛；更不必一开始就承担整个 4B 模型的部署。

**最值得保留的总体方向：用编译保证操作的可靠性，用学习处理解释与选择，再用因果实验判断二者结合是否产生了新的能力。**
